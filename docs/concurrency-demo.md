# 高并发抢课与原子防超卖演示指南 (Concurrency Demo Guide)

本指南面向课程期末答辩与项目演示，专门介绍教务选课系统在**高并发瞬时抢课**、**数据库原子更新 (CAS)**、**零超卖守卫**等核心数据库特性的演示方法与底层原理。

---

## 1. 为什么答辩必须重点展示“并发防超卖”？

在数据库系统与选课系统设计中，最核心的考点就是**并发事务与数据一致性**：
- **传统先查后写 (Read-Then-Write) 缺陷**：
  若采用 `SELECT current_capacity` 判断未满，再执行 `UPDATE` + `INSERT`，在多名学生毫秒级同时抢课时，会发生**脏读与超卖 (Oversell)**，导致 50 人的课程选进 55 人。
- **本系统原子 CAS 解决方案**：
  采用行级原子比较与替换（Compare-And-Swap）条件更新：
  ```sql
  UPDATE course_offerings
  SET current_capacity = current_capacity + 1
  WHERE id = ? AND current_capacity < max_capacity;
  ```
  结合 `rowsAffected === 1` 判定，保证即使数千请求并发涌入，**也绝不会有任何多余名额流出**。

## 4. 底层架构与事务安全机制

```mermaid
sequenceDiagram
    autonumber
    actor StuA as 学生 A (苏晓彤)
    actor StuB as 学生 B (赵文杰)
    participant Server as Hono 后端服务
    participant DB as SQLite / LibSQL

    Note over StuA,StuB: 教学班 off_ds_01 (49/50, 仅剩 1 名额)
    par 毫秒级瞬时并发
        StuA->>Server: POST /api/enrollments/enroll
        StuB->>Server: POST /api/enrollments/enroll
    end

    critical 原子条件更新 (CAS)
        Server->>DB: UPDATE course_offerings SET current_capacity + 1 WHERE current_capacity < max_capacity
        DB-->>Server: 学生 A 抢到名额 (rowsAffected = 1, current_capacity 变 50)
        Server->>DB: INSERT INTO enrollments (ACTIVE)
        Server-->>StuA: 201 Created (选课成功)
    and
        Server->>DB: UPDATE course_offerings SET current_capacity + 1 WHERE current_capacity < 50
        DB-->>Server: 学生 B 条件不满足 (rowsAffected = 0)
        Server-->>StuB: 409 Conflict (手慢了！名额已满)
    end
```

### 核心亮点
1. **无死锁轻量锁**：直接依靠 SQLite 行级排他原子操作，无需复杂的分布式锁组件即可保证严格一致；
2. **写失败即时回滚**：如果后续 `INSERT` 发生异常，系统自动执行补偿回滚（`current_capacity - 1`），保证容量计数永不漂移；
3. **退课状态智能激活**：退课后再次选课自动更新历史记录为 `ACTIVE`，避免产生重复脏行或违反唯一键。

## 5. 答辩高频提问 Q&A 速查清单

- **Q1：你们的选课系统如何防止超卖（Oversell）？**
  - **A**：我们在后端使用条件原子更新语句 `UPDATE ... WHERE current_capacity < max_capacity`。数据库引擎在执行时具备排他原子性，通过受影响行数判断是否获得配额，从根本上杜绝了脏读和并发超卖。

- **Q2：如果学生选课成功但插入选课明细失败了怎么办？**
  - **A**：我们的选课接口包含自动补偿机制。一旦在插入 `enrollments` 或审计日志时抛出异常，捕获块会立刻执行 `UPDATE course_offerings SET current_capacity = current_capacity - 1` 进行配额回退，保证数据自愈。

- **Q3：如何演示给评委老师看？**
  - **A**：可以直接运行 `pnpm demo:race` 在终端发起毫秒级高并发压测，实时打印两个请求的竞争胜负，并输出 SQLite 底层容量与行数的 100% 一致性校验结果。
